  1. WHAT IS DATAPILOT AI?
================================================================================

DataPilot AI is a fully automated, plug-and-play analytics platform. A user
uploads any dataset (CSV, Excel, SQL dump) or connects an external database
(PostgreSQL, MySQL, Snowflake, Firebase), and the system automatically:

  1. Ingests the data into a PostgreSQL data warehouse
  2. Uses Google Gemini AI to analyze the schema and pick meaningful columns
  3. Generates appropriate charts via Apache Superset
  4. Builds a RAG (Retrieval-Augmented Generation) chatbot so the user can
     ask natural language questions about their data

The entire process — from upload to a fully interactive dashboard with a
chatbot — happens automatically in the background.

  6. THE CORE AI PIPELINE  (6 Steps — runs in background)
================================================================================

When the user uploads a file or connects a database, the pipeline runs
automatically as a FastAPI BackgroundTask. The frontend polls the pipeline
status endpoint every 2 seconds to show real-time progress.

STEP 1: DATA INGESTION
───────────────────────
  Trigger: POST /api/ingest/upload or POST /api/connect/connect
  
  For FILE UPLOADS (CSV / Excel / SQL dump):
    a. File is saved to /tmp/datapilot/uploads/{uuid}.{ext}
    b. IngestionService reads it using pandas:
       - CSV  → pd.read_csv()
       - Excel → pd.read_excel()
       - SQL   → regex parsing of INSERT statements → DataFrame
    c. Column names are normalized to lowercase (e.g. "First Name" → "first_name")
    d. DataFrame is bulk-inserted into a new PostgreSQL table named "ds_{uuid}"
    e. Schema is extracted: column names, types, sample values, null %, cardinality
  
  For DATABASE CONNECTIONS (PostgreSQL / MySQL / Snowflake / Firebase):
    a. ExternalDBConnector tests connectivity
    b. Extracts schema by querying information_schema.columns (SQL DBs)
       or by sampling Firestore documents (Firebase)
    c. No data is ingested yet (that happens in Step 5 for Firebase)
  
  Result: raw_schema JSON stored in datasets.raw_schema
  Status: "ingested"

STEP 2: SCHEMA EXTRACTION
──────────────────────────
  This is a pass-through step that confirms the schema was mapped correctly.
  Result: Immediate success.

STEP 3: GEMINI AI SCHEMA ANALYSIS
──────────────────────────────────
  The raw_schema JSON is sent to Gemini (or Groq as fallback) with a detailed
  prompt asking the AI to:
  
  a. Classify each column as: "metric" (numeric values to measure),
     "dimension" (categorical values to group by), or "skip" (IDs, passwords, etc.)
  b. Suggest 4-8 meaningful charts with:
     - Chart type (bar, line, pie, area, scatter, table, big_number)
     - X-axis column, Y-axis column, aggregation function
     - SQL query using {{table}} placeholder
     - Reasoning for why this chart is insightful
  c. Identify key metrics, time columns, primary dimensions
  d. Write a 2-3 sentence data summary
  e. Determine if the data is valid for analytics (is_valid_for_analytics flag)
  
  CRITICAL RULE: The AI is instructed to only use SUM/AVG on numeric columns,
  and COUNT on text/categorical columns. The pipeline also verifies this
  against the actual PostgreSQL column types as a safety net.
  
  Result: ai_schema JSON stored in datasets.ai_schema
  Status: "ai_analyzing" → "ai_done"

STEP 4: AI DATA SELECTION
──────────────────────────
  Extracts the selected columns and suggested charts from the AI analysis.
  Validates that at least 1 column and 1 chart suggestion exist.
  If validation fails, the pipeline STOPS — no charts are generated.
  
  Result: Column list and chart queue prepared
  Status: "ai_done"

STEP 5: SUPERSET PUSH (Chart & Dashboard Generation)
─────────────────────────────────────────────────────
  This is the most complex step. For each AI-suggested chart:
  
  a. REGISTER THE DATABASE with Superset:
     - For file uploads: registers the main datapilot warehouse PostgreSQL
     - For external DBs: registers the external DB connection URI
     - For Firebase: data is first ingested into PostgreSQL (since Superset
       has no native Firebase connector), then the warehouse DB is registered
  
  b. CREATE A SUPERSET DATASET pointing to the warehouse table
  
  c. FOR EACH SUGGESTED CHART:
     1. Determine the correct Superset viz_type:
        - If x-axis is a date column → use echarts_timeseries_bar/line/area
        - If x-axis is categorical → use dist_bar (categorical bar chart)
        - Pie → pie, Scatter → echarts_scatter, Table → table
     2. Build the metric object with safe aggregation:
        - Numeric columns: SUM, AVG, etc.
        - Text columns: COUNT only (AVG/SUM on text would cause errors)
        - Extra safety: queries PostgreSQL information_schema to verify
          the actual column type before choosing the aggregation
     3. Build chart_params with groupby, metrics, filters, etc.
     4. Call Superset REST API to create the chart
     5. Save a Chart record in the local database
  
  d. CREATE A SUPERSET DASHBOARD:
     1. Create the dashboard via Superset API
     2. Build a grid layout with ROW/COLUMN/CHART positions
     3. Link all charts to the dashboard
  
  Result: Superset dashboard ready with all charts
  Status: "superset_ready"

STEP 6: RAG EMBEDDING
──────────────────────
  Builds the knowledge base for the RAG chatbot:
  
  a. Create text chunks from:
     - Data summary from AI analysis
     - Column descriptions (name, type, role, reason)
     - Sample data rows from the warehouse (up to 200 rows, batched in groups
       of 25 for efficiency)
  
  b. For each chunk:
     - Call Gemini Embedding API (model: gemini-embedding-001)
     - Get a 3072-dimensional vector
     - Store in chunk_embeddings table
     - Rate-limited: pauses every 5 requests to avoid API quotas
  
  Result: Embedding vectors stored for similarity search
  Status: Pipeline complete

================================================================================
  7. RAG CHATBOT — HOW IT WORKS
================================================================================

When the user sends a message on the Chat page, here is the full flow:

  1. EMBED THE QUERY
     - User's question is embedded using Gemini Embedding API
       (task_type: "retrieval_query")

  2. RETRIEVE RELEVANT CHUNKS
     - All chunk_embeddings for this dataset are loaded
     - Cosine similarity is computed between the query vector and each
       stored embedding (pure Python implementation)
     - Top 8 most similar chunks are selected

  3. DETECT INTENT
     The RAG engine classifies the user's message into one of three intents:
     
     a. CHART MODIFICATION: "change the bar chart to pie"
        - Detects keywords like "change", "convert", "switch"
        - Matches the target chart by title (substring or word overlap)
        - Updates the Superset chart's viz_type via API
        - Returns confirmation to the user
     
     b. CHART CREATION: "show me a bar chart of sales by region"
        - Detects keywords like "chart", "graph", "visualize"
        - Generates SQL via Gemini (using the schema context)
        - Executes the SQL against the warehouse
        - Builds a native Chart.js-compatible data structure
        - Also creates a persistent Superset chart and adds it to dashboard
     
     c. DATA QUESTION: "what is the total revenue?"
        - No chart-related keywords detected
        - Falls through to the grounded answer step

  4. GENERATE GROUNDED ANSWER
     - The retrieved chunks + conversation history + data summary are sent
       to Gemini with a prompt: "Answer using ONLY the data provided"
     - Gemini generates a natural language answer
     - If a chart was also created, it is appended to the response

  5. RETURN RESPONSE
     The response includes:
     - answer: The AI-generated natural language answer
     - sql_generated: The SQL query (if any was generated)
     - chart_data: Chart.js-compatible data for rendering inline
     - new_chart_id: Superset chart ID (if created)
     - sources: Snippets from the retrieved chunks

================================================================================
  10. AI SERVICES — GEMINI & GROQ
================================================================================

The project supports two AI providers with automatic failover:

PRIMARY: Google Gemini
  - Model: gemini-2.0-flash (configurable)
  - Embedding Model: gemini-embedding-001 (3072 dimensions)
  - Used for: schema analysis, SQL generation, RAG answers, embeddings

FALLBACK: Groq (via HTTP API)
  - Model: llama-3.3-70b-versatile
  - Activated when USE_GROQ=True in environment
  - Used for: text generation only (not embeddings)
  - Embeddings ALWAYS use Gemini regardless of the USE_GROQ flag

RETRY LOGIC:
  - Text generation: 3 retries with exponential backoff (2s, 4s, 8s)
  - Embeddings: 5 retries with linear backoff (2s, 4s, 6s, 8s, 10s)
  - Automatic failover from Gemini → Groq on quota exhaustion

================================================================================
  14. KEY DESIGN DECISIONS
================================================================================

  1. NO DEFAULT CHARTS
     Charts are only generated after Gemini AI analysis. If the AI determines
     the data has no meaningful patterns (is_valid_for_analytics: false), the
     pipeline halts and no dashboard is created.

  2. TWO EXCLUSIVE INPUT MODES
     Upload (files) and Connect (databases) are separate, independent paths.
     Both funnel into the same 6-step AI pipeline.

  3. 100% RAG CHATBOT
     The chatbot never uses hardcoded or template answers. Every response:
     - Embeds the query with Gemini
     - Retrieves relevant data chunks via cosine similarity
     - Generates a grounded answer using only the retrieved context

  4. PER-USER DATA ISOLATION
     Each user only sees their own datasets, charts, and dashboards.
     Superset dashboards are accessed via short-lived guest tokens.

  5. AGGREGATION SAFETY
     The pipeline verifies column types at multiple levels:
     - AI prompt instructs numeric-only aggregations
     - Python code checks the schema type mapping
     - Extra safety queries PostgreSQL information_schema
     This prevents "AVG on TEXT column" errors.

  6. DUAL AI PROVIDER STRATEGY
     Gemini is primary; Groq (Llama 3.3) is the fallback. Embeddings always
     use Gemini since Groq doesn't offer an embedding API.

  7. NATIVE CHART RENDERING
     The dashboard page uses Chart.js to render charts natively in the
     browser, rather than relying solely on Superset iframe embedding.
     This provides faster loading and better UI integration.

  8. BACKGROUND PIPELINE
     The entire AI pipeline runs as a FastAPI BackgroundTask, so the upload
     API returns immediately (202 Accepted). The frontend polls for status.

================================================================================
  15. COMPLETE USER JOURNEY — END TO END
================================================================================

  1. User opens http://localhost → sees Login page
  2. User clicks "Create Account" → fills form → account created
  3. User lands on Overview page (empty — no datasets yet)
  4. User navigates to "Data Source" page
  5. User drags a CSV file into the upload zone
  6. Backend saves the file, creates a Dataset record, returns 202
  7. Frontend redirects to Pipeline page
  8. Pipeline runs in background:
     a. Pandas reads CSV → bulk inserts into PostgreSQL as "ds_{uuid}"
     b. Schema extracted: column names, types, sample values
     c. Schema sent to Gemini AI → AI returns column classifications + charts
     d. AI selections validated (≥1 column, ≥1 chart)
     e. Charts created in Superset → dashboard assembled
     f. RAG embeddings built for chatbot
  9. Frontend shows each step completing in real-time (polling every 2s)
  10. Pipeline completes → "View Dashboard" button appears
  11. User clicks → sees Dashboard page with Chart.js-rendered charts
  12. User navigates to Chat page
  13. User asks: "What are the top 5 categories by revenue?"
  14. RAG engine:
      a. Embeds the question
      b. Finds relevant data chunks
      c. Detects "chart creation" intent
      d. Generates SQL via Gemini
      e. Executes SQL, builds chart data
      f. Creates Superset chart + adds to dashboard
      g. Returns answer + inline chart
  15. User sees the answer with a chart rendered below it
  16. User asks: "Change that bar chart to a pie chart"
  17. RAG engine detects "chart modification" intent
  18. Updates the Superset chart viz_type → confirms to user
  19. Dashboard page now reflects the updated chart type
